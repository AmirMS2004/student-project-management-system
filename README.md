# سامانه مدیریت پروژه‌های دانشجویی

بک‌اند: Python (FastAPI + SQLAlchemy + SQLite)
فرانت‌اند: JavaScript (React + Vite)

> این ریپو فقط برای نمایش (نمونه‌کار) عمومیه. کپی، اجرا، تغییر یا استفاده از این کد بدون اجازه‌ی صریح صاحب پروژه مجاز نیست — بخش [LICENSE](LICENSE) رو ببینید.

## ساختار پروژه

```
backend/    سرور API (FastAPI)
frontend/   رابط کاربری (React)
```

## اجرای بک‌اند

```bash
cd backend
python -m venv venv
venv\Scripts\activate        # ویندوز (PowerShell: venv\Scripts\Activate.ps1)
pip install -r requirements.txt
alembic upgrade head         # ساخت/به‌روزرسانی جداول دیتابیس
uvicorn app.main:app --reload --port 8000
```

سرور روی `http://127.0.0.1:8000` بالا می‌آید. مستندات تعاملی API: `http://127.0.0.1:8000/docs`

## مدیریت دیتابیس با Alembic

دیگر لازم نیست بعد از هر تغییر در مدل‌ها فایل `app.db` را پاک کنید. به‌جایش:

```bash
cd backend
alembic upgrade head
```

این دستور دیتابیس را بدون از دست رفتن داده‌ها به آخرین نسخه‌ی مدل‌ها به‌روز می‌کند. اگر `app.db` اصلاً وجود نداشته باشد، همین دستور آن را از صفر می‌سازد.

**وقتی مدلی را در `app/models.py` تغییر می‌دهید** (فیلد جدید، جدول جدید و…)، این دو دستور را به ترتیب اجرا کنید:

```bash
alembic revision --autogenerate -m "توضیح کوتاه تغییر"
alembic upgrade head
```

دستور اول یک فایل migration جدید در `backend/alembic/versions/` می‌سازد (حتما محتوایش را نگاه کنید، گاهی autogenerate نیاز به اصلاح دستی دارد)، دستور دوم آن را اجرا می‌کند. این فایل‌ها باید در گیت commit شوند — بخشی از تاریخچه‌ی پروژه‌اند.

⚠️ **محدودیت شناخته‌شده‌ی autogenerate:** تغییر مقادیر مجاز یک ستون `Enum` (مثلا اضافه کردن یک نقش جدید به `UserRole`) را autogenerate تشخیص نمی‌دهد و migration خالی تولید می‌کند — باید آن را دستی بنویسید (نمونه‌اش را در `alembic/versions/cc0c09881608_add_admin_role.py` ببینید که از `batch_alter_table` استفاده می‌کند، چون SQLite نمی‌تواند CHECK constraint را مستقیم ALTER کند).

برای برگرداندن یک مرحله به عقب: `alembic downgrade -1`

## داده‌های نمونه (Seed)

برای این‌که هر بار مجبور نباشید از صفر چند کاربر و پروژه دستی بسازید، یک اسکریپت seed هست که چند استاد، چند دانشجو، و چند پروژه با وضعیت‌های مختلف (باز، در حال انجام، خاتمه‌یافته) به همراه جلسه/گزارش/نمره/پیام نمونه می‌سازد:

```bash
cd backend
python seed.py
```

اجرای دوباره‌اش بی‌خطر است (idempotent) — کاربر یا پروژه‌ای که با همان عنوان/ایمیل از قبل وجود دارد دوباره ساخته نمی‌شود.

رمز عبور همه‌ی کاربران نمونه: `password123`

| ایمیل | نقش |
|---|---|
| admin@example.com | مدیر گروه |
| professor1@example.com | استاد (دکتر احمدی) |
| professor2@example.com | استاد (دکتر رضایی) |
| student1@example.com | دانشجو (پروژه در حال انجام دارد) |
| student2@example.com | دانشجو (یک درخواست در انتظار تایید دارد) |
| student3@example.com | دانشجو (پروژه‌اش خاتمه یافته) |
| student4@example.com | دانشجو (یک درخواست در انتظار تایید دارد) |

از VS Code هم می‌توانید با `Terminal > Run Task... > DB: Seed sample data` همین کار را انجام دهید.

## نقش مدیر گروه (Admin)

سامانه سه نقش دارد: دانشجو، استاد راهنما، و **مدیر گروه**. برخلاف دو نقش دیگر، حساب مدیر گروه **از طریق فرم ثبت‌نام عمومی قابل ساخت نیست** — حتی با کد دعوت — چون این بالاترین سطح دسترسی سامانه است و نباید خوداظهاری باشد. تنها راه ساختنش این اسکریپت است:

```bash
cd backend
python create_admin.py --name "نام مدیر" --email admin@example.com --phone 09120000000
```

(اگر `--password` ندهید، به‌صورت تعاملی پرسیده می‌شود.) دیتابیس seed‌شده هم از قبل یک حساب مدیر گروه دارد: `admin@example.com` / `password123`.

مدیر گروه می‌تواند:
- آمار سراسری کل سامانه را ببیند (تعداد اساتید، دانشجوها، پروژه‌ها با هر وضعیت، میانگین مدت و پیشرفت) — نه فقط آمار یک استاد.
- همه‌ی پروژه‌های سامانه را با جزئیات کلی‌شان (عنوان، استاد، دانشجو، وضعیت، پیشرفت) ببیند، صرف‌نظر از این‌که مالک آن پروژه است یا نه.
- لیست کامل کاربران سامانه را ببیند و بر اساس نقش فیلتر کند.

دسترسی مدیر گروه عمداً به همین سطح «نظارت کلی» محدود شده — به جزئیات خصوصی هر پروژه (پیام‌ها، گزارش‌های هفتگی، فایل‌های تبادل‌شده بین استاد و دانشجو) دسترسی ندارد، چون آن‌ها ارتباط خصوصی استاد-دانشجو هستند.

## تست‌های خودکار (pytest)

بک‌اند یک مجموعه تست کامل دارد که مسیرهای اصلی (ثبت‌نام+کپچا+کد دعوت، انتخاب پروژه، جلسات، گزارش‌ها، نمرات، فایل‌ها، پیام‌ها، اعلان‌ها، داشبورد) و همچنین کنترل دسترسی نقش‌محور را پوشش می‌دهد. هر تست دیتابیس و پوشه‌ی آپلود موقت و ایزوله‌ی خودش را دارد، پس هرگز به `app.db` یا `uploads/` واقعی شما دست نمی‌زند و اجرای Alembic هم لازم ندارد.

```bash
cd backend
pytest
```

از VS Code: `Terminal > Run Task... > Test: Run backend tests (pytest)`، یا از تب Testing (آیکون قلمه‌آزمایش در نوار کناری) که به‌طور خودکار تست‌ها را شناسایی می‌کند.

هر وقت یک مسیر جدید یا قانون دسترسی جدید به بک‌اند اضافه کردید، یک تست هم برایش در `backend/tests/` اضافه کنید — این‌طوری دفعه‌ی بعد که چیزی را تغییر می‌دهید، به‌جای تست دستی از اول، فقط کافی است `pytest` را اجرا کنید.

## اجرای فرانت‌اند

Node.js (نسخه LTS) روی سیستم نصب شده است. برای اجرا:

```bash
cd frontend
npm install
npm run dev
```

فرانت روی `http://localhost:5173` بالا می‌آید و درخواست‌های `/api` را به بک‌اند (پورت 8000) پراکسی می‌کند.
(اگر بعد از نصب Node.js دستور `node`/`npm` در ترمینال شناخته نشد، یک ترمینال جدید باز کنید تا PATH آپدیت‌شده بارگذاری شود.)

## اجرا با VS Code

پوشه `Project Code` را در VS Code باز کنید (`File > Open Folder...`). یک پیکربندی آماده در `.vscode/` قرار دارد:

- **یک‌کلیکی:** `Terminal > Run Task... > Run Backend + Frontend` هر دو سرور را هم‌زمان در دو ترمینال جدا اجرا می‌کند.
- **جداگانه:** از همان منو می‌توانید فقط `Run Backend (FastAPI)` یا فقط `Run Frontend (Vite)` را اجرا کنید.
- **دیباگ بک‌اند:** تب Run and Debug (Ctrl+Shift+D) و انتخاب `Backend: FastAPI (debug)` امکان breakpoint گذاشتن روی کد پایتون را می‌دهد (به extension رسمی Python نیاز دارد).
- تب `پروژه‌ها` توصیه‌شده در `.vscode/extensions.json` (Python، ESLint، Prettier) را نصب کنید تا VS Code پیشنهاد کند.

نکات:
- قبل از اولین اجرا حتما طبق بخش‌های بالا `pip install -r requirements.txt` (در `backend/venv`) و `npm install` (در `frontend`) را یک‌بار در ترمینال اجرا کرده باشید؛ تسک‌ها فقط سرورها را بالا می‌آورند و نصب نمی‌کنند.
- اگر Node.js را تازه نصب کرده‌اید و VS Code از قبل باز بوده، یک‌بار VS Code را کامل ببندید و دوباره باز کنید تا PATH جدید در ترمینال‌های داخلی آن اعمال شود.

## قابلیت‌های پیاده‌سازی‌شده

**استاد راهنما**
- تعریف موضوع پروژه (همراه با فایل توضیحات تکمیلی اختیاری) و جست‌وجو در پروژه‌های خودش
- تأیید/رد درخواست انتخاب پروژه
- تعیین زمان جلسات و ثبت گزارش جلسات
- تعیین موعد هفتگی تحویل گزارش (یک روز هفته + ساعت ثابت، مثلا «هر یکشنبه ساعت ۲۳:۵۹»)، قابل‌ویرایش از تب کلیات؛ این موعد به‌صورت خودکار هر هفته در رویدادهای پیش‌روی دانشجو تکرار می‌شود
- ثبت نمره هر مرحله؛ ثبت دوباره‌ی نمره برای همان مرحله (مثلا «پروپوزال») به‌جای ساختن ردیف تکراری، نمره‌ی قبلی را ویرایش می‌کند، و نمره‌ی نهایی پروژه (میانگین همه‌ی مراحل) به‌صورت خودکار در تب کلیات و تب نمرات نمایش داده می‌شود
- ثبت/بارگذاری فایل‌های موردنیاز
- ارسال پیام (همراه با پیوست فایل) برای دانشجو و مشاهده پیام‌های دانشجو
- مشاهده و ویرایش پیشرفت پروژه
- تعیین/ویرایش تاریخ و ساعت دفاع پروژه (دانشجو در صورت تغییر، اعلان دریافت می‌کند)
- ثبت **نتیجه رسمی دفاع** («قبول»، «نیاز به اصلاح»، «رد») همراه با توضیح اختیاری، از تب کلیات؛ در پرونده‌ی PDF هم درج می‌شود
- تایید/رد **زمان جلسه‌ی پیشنهادی دانشجو** (تب جلسات): علاوه بر تعیین مستقیم زمان جلسه، دانشجو می‌تواند زمانی را پیشنهاد دهد و استاد تایید/رد کند؛ تایید، جلسه‌ی واقعی را می‌سازد (دقیقا مثل فلوی درخواست انتخاب پروژه)
- دریافت اعلان یادآوری ۲۴ ساعت پیش از جلسات و جلسه‌ی دفاعی که خودش تعیین کرده
- داشبورد آماری (تعداد پروژه‌ها، فعال، خاتمه‌یافته، میانگین مدت انجام، درصد پیشرفت)، همراه با نمودار درصد پیشرفت هر پروژه به‌تفکیک و نمودار خطی روند نمره‌ی نهایی پروژه‌ها
- تب «رویدادهای پیش‌رو» در نوار بالا: فهرست زمانی جلسات و تاریخ‌های دفاع پروژه‌های خودش
- خروجی PDF پرونده‌ی پروژه (دکمه‌ی «دانلود پرونده PDF» در تب کلیات): شامل عنوان، چکیده، استاد/دانشجو، وضعیت و درصد پیشرفت، تاریخ و نتیجه‌ی جلسه دفاع، همه‌ی گزارش‌های هفتگی، و جدول نمرات به همراه نمره‌ی نهایی — برای ارائه در جلسه‌ی دفاع یا آرشیو دانشگاه
- خروجی ZIP آرشیو کامل پروژه (دکمه‌ی «دانلود آرشیو ZIP» کنار دکمه‌ی PDF): همان پرونده‌ی PDF به‌همراه تمام فایل‌های آپلودی پروژه (فایل توضیحات تکمیلی، فایل‌های تب «فایل‌ها»، پیوست گزارش‌ها، پیوست پیام‌ها) در پوشه‌های جدا، در یک فایل فشرده — برای آرشیو کامل دانشگاه

**مدیر گروه (Admin)**
- داشبورد آماری سراسری کل سامانه (نه فقط یک استاد): تعداد اساتید، دانشجوها، پروژه‌ها به تفکیک وضعیت، میانگین مدت و پیشرفت
- مشاهده‌ی همه‌ی پروژه‌های سامانه با استاد/دانشجوی هرکدام، صرف‌نظر از مالکیت
- مشاهده و فیلتر کاربران سامانه بر اساس نقش
- تغییر **کد دعوت ثبت‌نام استاد** از صفحه‌ی «تنظیمات» بدون نیاز به تغییر متغیر محیطی یا ری‌استارت سرور — مفید برای وقتی کد قبلی لو رفته یا برای دوره‌ی جدید باید عوض شود
- ساخت این حساب فقط از طریق اسکریپت `create_admin.py` ممکن است، نه ثبت‌نام عمومی (بخش «نقش مدیر گروه» را ببینید)

**دانشجو**
- مشاهده پروژه‌های قابل انتخاب، جست‌وجو در عنوان/چکیده و فیلتر کردن آن‌ها بر اساس استاد
- درخواست انتخاب پروژه
- دانلود فایل توضیحات تکمیلی پروژه (حتی پیش از انتخاب شدن، تا وقتی پروژه باز است)
- بارگذاری فایل‌ها
- مشاهده نظر استاد روی گزارش‌ها
- ثبت گزارش هفتگی (همراه با پیوست فایل اختیاری)
- مشاهده زمان جلسات و **پیشنهاد زمان جلسه** (تب جلسات): در کنار جلساتی که استاد تعیین می‌کند، دانشجو می‌تواند زمانی پیشنهاد بدهد و وضعیت آن (در انتظار/تایید‌شده/رد‌شده) را در همان تب پیگیری کند
- مشاهده تاریخ و نتیجه‌ی دفاع (در صورت ثبت توسط استاد)
- تب «رویدادهای پیش‌رو» در نوار بالا: فهرست زمانی جلسات، تاریخ دفاع، و موعد هفتگی تحویل گزارش پروژه‌ی خودش (اگر استاد آن را تعیین کرده باشد)، به‌ترتیب زمانی و گروه‌بندی‌شده بر اساس روز
- دریافت اعلان‌ها (تایید/رد درخواست، پیام جدید، نمره جدید، گزارش جلسه، فایل جدید، تصمیم استاد روی پیشنهاد زمان جلسه، و یادآوری ۲۴ ساعت پیش از جلسه/دفاع/موعد گزارش هفتگی) که با کلیک روی هرکدام مستقیم به صفحه‌ی مربوطه هدایت می‌شود
- مشاهده درصد پیشرفت و نمره‌ی نهایی (میانگین نمرات همه‌ی مراحل)
- ارسال پیام/سوال (همراه با پیوست فایل) به استاد
- دانلود پرونده‌ی PDF و آرشیو ZIP پروژه‌ی خودش (برای جلسه‌ی دفاع یا آرشیو شخصی)

**امنیت ثبت‌نام**
- کد امنیتی تصویری (CAPTCHA) تولیدشده در سمت سرور، یک‌بارمصرف و با انقضای ۵ دقیقه‌ای
- دریافت اجباری شماره موبایل برای همه‌ی کاربران (فرم `09xxxxxxxxx`)
- جلوگیری از ثبت‌نام با ایمیل یا شماره موبایل تکراری
- ثبت‌نام با نقش «استاد راهنما» نیازمند وارد کردن یک **کد دعوت** است تا دانشجویان نتوانند برای خودشان حساب استاد بسازند. مقدار پیش‌فرض این کد برای توسعه `dev-professor-code` است (متغیر محیطی `PROFESSOR_INVITE_CODE` در `backend/app/config.py`، فقط برای اولین اجرا)؛ از آن به بعد مدیر گروه می‌تواند از صفحه‌ی «تنظیمات» همین کد را از پنل مدیریت تغییر بدهد، بدون دست‌زدن به متغیر محیطی یا ری‌استارت سرور.

**تجربه کاربری**
- نشانگر دات قرمز کنار هر تب از صفحه‌ی پروژه (درخواست‌ها، جلسات، گزارش‌ها، نمرات، فایل‌ها، پیام‌ها، کلیات) وقتی محتوای جدیدی برای آن بخش ثبت شده و هنوز دیده نشده باشد؛ با باز کردن همان تب، دات پاک می‌شود
- کلیک روی هر اعلان در زنگوله‌ی اعلان‌ها مستقیم به صفحه‌ی پروژه‌ی مرتبط هدایت می‌کند
- دکمه‌ی تغییر حالت روشن/تاریک در نوار بالا (🌙/☀️)، با به‌خاطرسپاری انتخاب کاربر در مرورگر
- رابط کاربری روی صفحه‌ی موبایل ریسپانسیو است: منوی بالا روی صفحه‌ی کوچک به‌صورت منوی همبرگری (☰) جمع می‌شود و جدول‌ها (لیست پروژه‌ها، درخواست‌ها، نمرات، فایل‌ها) به‌جای بیرون‌زدن از صفحه، خودشان به‌صورت افقی اسکرول می‌شوند
- **ویرایش پروفایل** (هر دو نقش): از صفحه‌ی «پروفایل» (لینک در منوی بالا یا کلیک روی نام کاربری) می‌توان نام، ایمیل و شماره موبایل را ویرایش کرد (با همان چک‌های یکتا بودن ایمیل/موبایل که در ثبت‌نام هست) و رمز عبور را با وارد کردن رمز فعلی تغییر داد
- **پیش‌نمایش فایل**: فایل‌های PDF و تصویر (jpg، png، gif، webp، svg، bmp) به‌جای دانلود اجباری، در یک تب جدید با نمایشگر داخلی مرورگر باز می‌شوند («مشاهده»)؛ بقیه‌ی فرمت‌ها مثل قبل دانلود می‌شوند («دانلود»). این رفتار برای همه‌ی فایل‌های سامانه یکسان است: فایل توضیحات تکمیلی پروژه، فایل‌های تب «فایل‌ها»، پیوست گزارش هفتگی، و پیوست پیام‌ها
- **تقویم شمسی در کل سامانه**: همه‌ی تاریخ‌ها (تاریخ شروع/پایان/دفاع پروژه، زمان جلسات، تاریخ گزارش‌ها/نمرات/فایل‌ها/پیام‌ها/اعلان‌ها، و خروجی PDF) فقط به‌صورت شمسی و با ارقام فارسی نمایش داده می‌شوند؛ فرم‌های ویرایش تاریخ (تاریخ شروع/پایان/دفاع در تب کلیات، زمان جلسه در تب جلسات) هم به‌جای تقویم میلادی مرورگر، از یک تقویم شمسی اختصاصی (`react-multi-date-picker`) استفاده می‌کنند

## نکات فنی

- احراز هویت با JWT (هدر `Authorization: Bearer <token>`)
- دیتابیس SQLite در فایل `backend/app.db`، ساخته و به‌روزرسانی‌شده توسط Alembic (بخش «مدیریت دیتابیس با Alembic» را ببینید). دیگر نیازی به پاک کردن دستی این فایل بعد از تغییر مدل‌ها نیست.
- فایل‌های آپلودی (فایل پروژه، پیوست پیام، فایل توضیحات تکمیلی) در `backend/uploads/` ذخیره می‌شوند
- کد CAPTCHA به‌صورت درون‌حافظه‌ای (in-memory) در پردازه‌ی سرور نگه‌داری می‌شود؛ یعنی با ری‌استارت سرور یا در حالت چند-worker پاک می‌شود — برای این پروژه دانشجویی با یک سرور تک-پردازه‌ای کفایت می‌کند
- برای production حتما مقدار `SECRET_KEY` را از طریق متغیر محیطی تغییر دهید
- خروجی PDF (`app/pdf_export.py`) با کتابخانه‌ی `reportlab` ساخته می‌شود و برای چیدمان درست متن فارسی (شکل‌دهی حروف + راست‌به‌چپ) از `arabic-reshaper` و `python-bidi` استفاده می‌کند. چون reportlab فونت فارسی داخلی ندارد، از فونت Tahoma/Arial که همراه ویندوز نصب است استفاده می‌شود؛ روی سیستم‌عامل دیگری اجرا شود باید مسیر یک فونت فارسی‌زبان به لیست `_FONT_CANDIDATES` در همان فایل اضافه شود
- تاریخ‌ها در سرور همیشه میلادی ذخیره و رد و بدل می‌شوند (ستون‌های `DateTime` معمولی، بدون منطق تقویم شمسی در دیتابیس یا API)؛ تبدیل به شمسی فقط در لایه‌ی نمایش انجام می‌شود: در فرانت با `toLocaleDateString/toLocaleString("fa-IR")` (خروجی مرکزی در `frontend/src/utils/date.js`) که به‌طور پیش‌فرض تقویم فارسی می‌دهد، و در PDF با کتابخانه‌ی پایتونی `jdatetime`
- تب رویدادهای پیش‌رو (`GET /api/calendar/events`) خروجی را در لحظه از سه منبع می‌سازد، بدون جدول جداگانه‌ی «رویداد»: جلسات (`Meeting`)، تاریخ دفاع پروژه، و موعد هفتگی گزارش (`Project.report_weekday` + `report_deadline_time`، که به‌صورت چند نمونه‌ی تکرارشونده در بازه‌ی ۴۵ روز آینده محاسبه می‌شود) — منطق مشترک در `app/calendar_events.py`
- یادآوری ۲۴ ساعته با یک تسک پس‌زمینه‌ی درون‌فرایندی (`app/reminders.py`, `reminder_loop`) پیاده شده که هر ۱۵ دقیقه دیتابیس را برای رویدادهای «فردا» بررسی می‌کند؛ برای جلوگیری از یادآوری تکراری، هر رویداد (با کلید یکتای `meeting:<id>`، `defense:<project_id>` یا `report:<project_id>:<تاریخ>`) در جدول `reminder_logs` ثبت می‌شود (این جدول در دیتابیس است، نه درون‌حافظه‌ای، پس با ری‌استارت سرور یادآوری تکراری ارسال نمی‌شود). این تسک فقط با اجرای واقعی سرور (`uvicorn`) شروع می‌شود، نه در تست‌ها — تست‌ها مستقیماً تابع `check_and_send_reminders(db)` را با سشن خودشان صدا می‌زنند
- پیشنهاد زمان جلسه از سمت دانشجو یک جدول جدا (`MeetingRequest`) دارد، دقیقا به همان الگوی `ProjectRequest` (وضعیت pending/approved/rejected + `decided_at`)؛ تایید آن یک ردیف واقعی در جدول `Meeting` می‌سازد، پس منطق تقویم و یادآوری (که فقط `Meeting` را می‌بینند) بدون تغییر برای جلسات تاییدشده هم کار می‌کند
- خروجی ZIP (`app/zip_export.py`) از همان `build_project_pdf` برای ساخت PDF داخل آرشیو استفاده می‌کند و فایل‌ها را مستقیم از پوشه‌ی آپلود (`file_storage.UPLOAD_DIR`) می‌خواند؛ نام‌گذاری فایل‌ها با پیشوند شناسه‌ی ردیف (مثلا `12-گزارش.pdf`) برای جلوگیری از برخورد نام در پوشه‌های «گزارش‌ها»/«فایل‌ها»/«پیام‌ها»
- تنظیمات قابل‌تغییر از پنل مدیریت (فعلاً فقط کد دعوت استاد) در یک جدول کلید/مقدار ساده نگه‌داری می‌شوند (`app_settings`، از طریق `app/settings.py`)؛ اگر مقداری هنوز در این جدول ثبت نشده باشد (مثلا بلافاصله بعد از migration)، همچنان مقدار پیش‌فرض `PROFESSOR_INVITE_CODE` از متغیر محیطی خوانده می‌شود، تا رفتار فعلی هیچ نصبی به‌هم نخورد
